# World Crokinole Rankings — Логика проекта (русский)

## 1. Назначение и стек

Приложение — веб-клиент на **Next.js 16** (App Router, React 19) для **турниров и событий** по крокинолу, **профилей игроков**, **клубов** и **мировых рейтингов**. Данные в **Supabase** (PostgreSQL, Auth, Storage). **Stripe** — оплата регистрации на события и подписок; вебхуки обновляют состояние подписки.

Локализация — **next-intl**, маршруты под `app/[locale]/`.

---

## 2. Архитектура на высоком уровне

| Слой | Роль |
|--------|------|
| `app/` | Маршруты, API handlers, layouts |
| `src/_pages/` | Состав страниц (server/client по необходимости) |
| `src/widgets/`, `src/shared/modules/` | Крупные блоки UI и переиспользуемые модули |
| `src/shared/supabase/data.ts` | Запросы и мутации к БД (клиент/сервер) |
| `supabase/migrations/` | Схема, RLS, SQL-функции (например `refresh_rankings`) |

Сессия Supabase на сервере через `createClient`. Критичные записи (результаты матчей, claim игрока) выполняются **service role** только на сервере.

## 3. Маршруты и поведение

### 3.1 `/{locale}` (корень локали)

Клиентская страница: **авторизован** → редирект на `/{locale}/dashboard`; **гость** → шаг 1 онбординга new-visitor.

### 3.2 `/{locale}/dashboard`

Подключает тот же модуль, что и **главная**: Hero, превью статистики, новости, превью рейтингов, события, клубы, блок подписки. То есть «дашборд» — **основная точка входа для вошедших**, отдельная вёрстка не используется.

### 3.3 Публичные / частично публичные страницы (с футером)

- **`/rankings`** — полный интерфейс рейтингов (те же данные, что на главной, обычно развёрнуто).
- **`/events`** — список событий и фильтры.
- **`/events/create`** — простое создание события (`CreateEventForm`). Для **бесплатного плана** (`subscription_plan` пустой или `standard`) — жёсткие ограничения.
- **`/events/create-tournament`** — пошаговое создание турнира: ranked/unranked, черновик, вместимость и т.д.
- **`/events/[id]`** — карточка события: регистрация, квалификационные раунды, сетка (если турнир), похожие события.
- **`/events/[id]/edit`** — редактирование организатором.
- **`/events/[id]/results`** — только **создатель события**, вошедший пользователь: ввод результатов (`EnterEventResultsForm` → API).
- **`/players`** — каталог с пагинацией, поиск, фильтры kingdom/club (`getPlayersWithFilters`).
- **`/players/[id]`** — публичный профиль: график рейтинга, матчи из `singles`/`doubles`, бейджи, блок «Top 8 tournaments» из таблицы `tournaments`.
- **`/clubs`**, **`/clubs/[id]`** — список клубов и страница клуба.
- **`/profile`** — аккаунт: подписка, блок турниров из таблицы `tournaments`, бейджи рейтинга/матчей, созданные события, мои клубы.
- **`/profile/edit`** — редактирование профиля.
- **`/membership-plans`** — тарифы / переход в Stripe checkout.
- **`/news/[id]`** — детальная страница новости (заголовок, дата, изображение, rich-text описание), `404` если id невалидный или запись не найдена.

### 3.4 Авторизация и онбординг (часто без футера)

- **`/auth/sign-in`**, **`/sign-up`**, **`/forgot-password`**, **`/reset-password`**
- **`/new-visitor/step-1` … `step-5`**, **`save-continue`**
- **`/claim-history`** — привязка исторических записей `match_history` к пользователю (`getMatchHistoryForClaim`).

### 3.5 Админка

- **`/{locale}/admin/sign-in`** — вход в админку.
- **`/{locale}/admin`** — клиентская консоль: события, игроки, клубы, турниры, рейтинги, история матчей, новости, профили, подписки (работа с Supabase из браузера для допущенных админов).
- Доступ к `/{locale}/admin*` определяется только флагом **`profiles.is_admin`**. Отдельной роли `superadmin` в коде сейчас нет.
- Проверка прав происходит и в UI (`useUserProfile`), и на API-роутах админки (`/api/admin/schema`, `/api/admin/table`): без `is_admin=true` вернётся `403 Forbidden`.
- Выдача доступа делается в Supabase SQL (пример):
  - `update profiles set is_admin = true where id = '<auth_user_uuid>';`
  - при необходимости снять доступ: `update profiles set is_admin = false where id = '<auth_user_uuid>';`
- После смены флага пользователю нужно перелогиниться (или обновить страницу), чтобы клиент подхватил новые права.
- Раздел **News / What's New**:
  - в списке таблиц админки это секция `news`;
  - создание/редактирование открывается отдельной формой `/{locale}/admin/news/new` и `/{locale}/admin/news/{id}/edit`;
  - поддерживаются поля `image`, `title`, rich-text `description`, `link_text`, `sort_order`, `created_at`;
  - картинка загружается в Supabase Storage bucket `news-images`, в БД хранится публичный URL.

## 4. Сущности предметной области (концептуально)

- **`players`** — запись игрока; опционально **`user_id`**. Поля отображения, **`rating`**, при наличии колонок — **`singles_rating`**, **`doubles_rating`**, счётчики побед / проценты.
- **`events`** — событие: формат (например турнир), **`is_ranked`**, даты, место, JSON **`tournament_bracket_results`**, **`qualifying_heats`**, **`created_by`**, видимость (draft), цена, вместимость.
- **`event_registrations`** — регистрации на событие.
- **`singles`** / **`doubles`** — записи **ранжируемых** матчей: игроки, победитель, поля Elo (`p*_rating_old/change/new`), `event_id`, `bracket_match_key`, детали в `match_detail`.
- **`rankings`** — **материализованный** лидерборд по категориям `laurels`, `singles`, `doubles`; заполняется **`refresh_rankings()`**.
- **`match_history`** — отдельная таблица для claim и наследия; не то же самое, что живые `singles`/`doubles` для графиков.
- **`news`**, **`clubs`**, **`tournaments`**, **`profiles`** — вспомогательные сущности.

## 5. Elo для турнирных матчей

Реализация: **`app/api/tournament-match-result/route.ts`**.

### 5.1 Одиночный разряд (singles)

- **K = 32**.
- Ожидаемый результат для игрока 1: \( E_1 = 1 / (1 + 10^{(R_2 - R_1)/400}) \).
- Фактический результат по **сетам**: победа 1, поражение 0, ничья 0.5.
- \(\Delta_1 = K \cdot (S_1 - E_1)\), округление до **двух знаков**; у второго игрока дельта с обратным знаком (тоже с округлением).
- Если рейтинга нет — база **1500** (поля `singles_rating` или `rating`).

### 5.2 Пары (doubles)

- Средний рейтинг команды 1 — среднее двух игроков (**doubles_rating**, иначе `rating`).
- Аналогично команда 2.
- Один шаг Elo между средними; **оба игрока команды получают одну и ту же дельту**, соответствующую их команде.

### 5.3 Когда считается рейтинг

- Только если у события **`is_ranked = true`**.
- Иначе обновляется лишь **`tournament_bracket_results`** (продвижение по сетке), без строк в `singles`/`doubles` и без Elo.

### 5.4 Правки и повторная отправка

- Ключ матча: **`event_id` + `bracket_match_key`**. Если запись есть — сначала **откат** прежних дельт на `players`, затем **update**; иначе **insert**.
- После этого — **`recomputePlayerAggregatesFromMatches`** для затронутых `players.id`, затем RPC **`refresh_rankings`** (best effort; при сбое возможен флаг `rankingsRefreshFailed` в ответе).

### 5.5 Права

- POST результатов — только пользователь, совпадающий с **`events.created_by`**.

### 5.6 Дата матча

- Берётся дата из **`start_date`** события (первые 10 символов); иначе **сегодня** (UTC-дата).

## 6. Агрегаты игрока (`recompute-player-aggregates-from-matches.ts`)

Для каждого затронутого **`players.id`**:

- Читаются все **`singles`** и **`doubles`** с участием игрока, по дате.
- **Победы / поражения / ничьи** из `winner` и стороны (P1/P2 или T1/T2).
- **Последний singles-рейтинг** — последний `p*_rating_new` в singles; **doubles** — аналогично из doubles.
- Обновляются счётчики, проценты побед (если колонки есть), **`rating`** / **`combined_rating`**: при двух дисциплинах — среднее последних singles и doubles; иначе `rating` по доступной дисциплине.

При отсутствии колонок win_pct/combined выполняется повторное обновление без этих полей.

## 7. Таблица `rankings` и `refresh_rankings()` (SQL)

Миграция: **`supabase/migrations/20250309120000_create_rankings_table.sql`**. При вызове функция **очищает и пересобирает** `rankings`.

### 7.1 Лавры (laurels) на игрока

- За последние **24 месяца** по каждому **календарному дню** суммируются **изменения рейтинга** (`rating_change`) по всем singles+doubles игрока → `day_score`.
- Берутся **8 лучших** дней по `day_score` на игрока.
- Вес: **1.0**, если дата матча в **последних 12 месяцах** (`match_date >= cutoff_12m`), иначе **0.75** (дни в окне **12–24 месяца** от «сегодня», всё ещё внутри 24-месячного отбора).
- **Laurels** = округлённая сумма `day_score * weight` по этим дням.

### 7.2 Категория singles

- Из **`singles`**: текущий **рейтинг** игрока — после **последнего** матча; суммируются wins/losses/ties.
- **Ранг** — `ROW_NUMBER` по убыванию рейтинга.
- **Тренд** — разница текущего рейтинга и рейтинга на отметке **90 дней назад** (последний матч на/до cutoff); формат `+x.xx`, отрицательное или `—`.

### 7.3 Категория doubles

- Та же схема, но источник — **`doubles`** (четыре слота игроков разворачиваются в строки для агрегации).

### 7.4 Категория laurels (как тип строк в `rankings`)

- Сортировка игроков по **`players.rating`** (комбинированный рейтинг профиля); в колонке laurels показывается посчитанная сумма лавров; тренд — относительно комбинированной истории singles+doubles за 90 дней.

Чтение: RLS разрешает **SELECT** всем.

## 8. Графики истории рейтинга (`getRatingHistoryFromSinglesDoubles`)

- Окно: **24 месяца** матчей.
- Серия строится из **`p*_rating_change`** по времени; начальный рейтинг — из `rating_old` первого матча или из `rating_new - change`.
- Месячные точки (текущий vs прошлый год) и строка **change** за окно.
- Используется на **профиле игрока**.

На загрузке профиля **`updatePlayerRatingsFromMatches`** может синхронизировать поля `players` с вычисленными итоговыми значениями (в фоне, без блокировки страницы).

## 9. События и турниры (логика UI)

- **Черновик турнира**: не создатель получает **404** на детальной странице.
- **Квалификационные heats**: регистрации по раундам; после окончания события подгружаются результаты heats.
- **`getGamesPlayedCount`**: для формата «пары» — **число пар − 1**; для одиночек — **участники − 1** (оценка числа игр).
- **Сетка**: состояние в **`tournament_bracket_results`**; продвижение победителя — **`tournament-bracket-winner-advance`**.

---

## 10. Подписки

- **`profiles.subscription_plan`**: например `standard` (бесплатный), `premium`, `administrator`.
- **Бесплатный план**: в **`CreateEventForm`** только **unranked**, **взнос 0**, не более **одного активного** события на пользователя.
- **Premium / administrator**: можно **ranked**, обычные цены; в Hero показываются кнопки создания события/турнира.
- **Stripe**: `app/api/stripe/*`.

---

## 11. Привязка игрока (claim)

**`POST /api/claim-player`**: пользователь привязывает существующую строку **`players`** к своему **`user_id`**, удаляет лишнюю авто-созданную запись с тем же `user_id`, сбрасывает `is_auto_created`.

| `tournament-match-result` | Elo, запись singles/doubles, сетка, агрегаты, `refresh_rankings` |

## 13. Поток данных (шпаргалка)

1. Организатор создаёт **ранжируемый** турнир → регистрации → ввод результатов → **`singles`/`doubles`** и **`players`** обновляются → **`refresh_rankings()`** → UI читает **`rankings`** через **`getRankings` / `getAllRankings`**.
2. **Лавры** на экранах приходят из SQL-алгоритма, не пересчитываются на клиенте отдельно.
3. Блок **«Top 8 tournaments»** на профиле — данные таблицы **`tournaments`**, не вывод из Elo-таблиц в коде.

4. Блок **What’s New** на главной/дашборде:
   - данные берутся из `news` через `getNews()`;
   - сортировка: сначала `sort_order` по возрастанию, затем `created_at` по убыванию;
   - на клиенте показывается пагинация по 3 карточки (`NewsClient` + `Pagination`);
   - если карточек на странице меньше 3, UI дорисовывает placeholder-элементы для сохранения сетки;
   - клик по карточке ведёт на `/news/{id}`, где данные запрашиваются через `getNewsById()`.
